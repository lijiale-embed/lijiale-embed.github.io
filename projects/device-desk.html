01 / 问题与个人工作

嵌入式设备的状态与排查信息需要有统一入口。这个个人练习把设备台账和异常工单放在同一条数据链路中，重点验证前后端协作、数据规则与结果留存。使用 AI 辅助完成页面、服务、数据库、测试与文档；不将本次新练习表述为既往商业项目或独立掌握的生产经验。

02 / 架构与数据流

浏览器 / 展示层表单、台账、筛选、详情HTML · CSS · JavaScript
→
HTTP / 业务层校验、路由、状态流转Express · JSON REST API
→
持久化 / 数据层设备、工单与关联约束SQLite · 参数化 SQL

浏览器通过 fetch 提交 JSON，服务端独立校验并执行参数化 SQL，返回统一的 data 或 error 结构。前端再刷新台账和工单；数据库保存 UTC 时间，浏览器按本地时间显示。页面不直接操作数据库。

选择原生前端便于跟踪每个请求；Express 简化路由与静态文件服务；SQLite 无需独立数据库服务，便于复现文件持久化；Node 内置测试工具直接验证真实 HTTP API。

03 / 设备与工单模块

  • 设备台账：新增、查看、编辑、删除；按名称 / 编号搜索和状态筛选；显示更新时间、模拟温湿度，未采样时允许空值。
  • 异常工单：关联设备、标题、描述、优先级与详情；支持搜索筛选，按“待处理 → 处理中 → 已关闭”流转并记录关闭时间。
  • 交互反馈：表单原生校验、请求中的按钮禁用、空数据提示、服务异常提示与刷新重试；详情支持原生 dialog 与 Escape 关闭。

04 / 数据设计与错误处理

两张表与关键约束
数据模型核心字段约束
devicesid、code、name、status、temperature、humidity、updated_atcode 唯一；状态与读数范围校验
ticketsid、device_id、title、description、priority、status、created_at、updated_at、closed_at设备外键；禁止删除关联设备；关闭不可重开

设备写入采用 POST / PUT / DELETE，工单通过 POST 创建、PATCH 更新状态，列表与详情使用 GET。重复设备编号、删除关联设备和非法状态流转返回 409；参数错误返回 400；资源不存在返回 404。JSON 请求体限制为 16 KB，错误信息统一展示，请求日志包含路径、状态码和耗时。

PATCH /api/tickets/1
Content-Type: application/json
{ "status": "in_progress" }

// 成功 → { "data": { "id": 1, "status": "in_progress", ... } }
// 非法流转 → HTTP 409
{ "error": { "code": "INVALID_TRANSITION", "message": "工单只能从待处理 → 处理中 → 已关闭，不可跳过或重开" } }

05 / 设计问题与解决方式

直接删除设备可能破坏工单历史，因此数据库使用外键 RESTRICT，接口在删除前返回可读的关联提示。重复提交或跳过工单处理会产生含糊的关闭记录，因此服务端检查当前状态，只接受下一步合法状态。详情与列表使用 textContent 展示用户内容，避免将输入解释为 HTML；SQL 通过占位参数传值。

为方便复现，示例仅通过 --seed 显式写入空库。正常重启不覆盖已有数据，测试使用隔离临时数据库，避免验收操作污染示例。

07 / 本地复现

下载完整源码并解压，安装 Node.js 24.x。在解压后的项目目录运行：

npm ci
npm start -- --seed
# 打开 http://127.0.0.1:3000

# 另开终端执行自动化测试
npm test

默认 SQLite 文件位于 data/device-desk.sqlite。停止并重新启动服务后，修改与工单状态继续保留。若端口占用，可配置 PORT；API 无响应先检查 /api/health 和服务日志。完整字段和 API 清单见 项目 README。
